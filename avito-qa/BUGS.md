## BUG-1. Любой пользователь может удалить чужое объявление

- **Серьёзность:** Critical (нарушение контроля доступа, потеря чужих данных)
- **Связанный тест:** `tests/test_security.py::test_cannot_delete_foreign_item` (TC-SEC-09)

**Шаги воспроизведения**

1. Зарегистрировать пользователей A и B (`POST /api/1/register`), получить токены (`POST /api/1/autorize`).
2. От имени A создать объявление (`POST /api/1/item`, `sellerID` = id пользователя A), запомнить UUID.
3. От имени B выполнить `DELETE /api/2/item/{uuid}` с токеном B.
4. От имени A выполнить `DELETE /api/2/item/{uuid}` (или `GET /api/1/item/{uuid}`).

**Фактический результат:** шаг 3 — 200 (пустое тело); шаг 4 — 404, объявление A удалено пользователем B.

**Ожидаемый результат:** шаг 3 — отказ (403, либо 404 без удаления); объявление остаётся доступным владельцу.

## BUG-2. Статистика удалённого объявления остаётся доступной

- **Серьёзность:** Major
- **Связанный тест:** `tests/test_statistics.py::test_statistics_after_delete` (TC-STAT-06)

**Шаги воспроизведения**

1. Создать объявление со статистикой `likes=21, viewCount=11, contacts=43`.
2. Удалить его (`DELETE /api/2/item/{id}`); убедиться, что `GET /api/1/item/{id}` возвращает 404.
3. Выполнить `GET /api/1/statistic/{id}` и `GET /api/2/statistic/{id}`.

**Фактический результат:** оба запроса возвращают 200 и `[{"contacts": 43, "likes": 21, "viewCount": 11}]`.

**Ожидаемый результат:** 404 `statistic <id> not found`, как для несуществующего объявления.

## BUG-3. Принимается отрицательная цена

- **Серьёзность:** Major
- **Связанный тест:** `tests/test_create_item.py::test_negative_price_rejected` (TC-ITEM-08)

**Шаги воспроизведения**

1. Авторизоваться, отправить `POST /api/1/item` с `"price": -1` и остальными корректными полями.
2. Выполнить `GET /api/1/{sellerID}/item`.

**Фактический результат:** 200 `Сохранили объявление - <uuid>`; в списке продавца объявление с `"price": -1`.

**Ожидаемый результат:** 400 с сообщением о некорректной цене, объявление не создаётся.

## BUG-4. Принимаются отрицательные значения статистики

- **Серьёзность:** Major
- **Связанный тест:** `tests/test_create_item.py::test_negative_statistics_rejected` (TC-ITEM-11)

**Шаги воспроизведения**

1. Отправить `POST /api/1/item` со `"statistics": {"likes": -1, "viewCount": 1, "contacts": 1}`.

**Фактический результат:** 200, объявление создано. Для `viewCount` и `contacts` поведение при отрицательных значениях подтвердите отдельно (в probe проверялся только `likes`).

**Ожидаемый результат:** 400, счётчики не могут быть отрицательными.

## BUG-5. `POST /api/1/register` с пустым объектом не отвечает

- **Серьёзность:** Major (зависание запроса; не подтверждён, см. примечание выше)
- **Связанный тест:** `tests/test_auth.py::test_register_invalid_body[пустой объект]` (TC-AUTH-04)

**Шаги воспроизведения**

1. `POST /api/1/register`, `Content-Type: application/json`, тело `{}`.

**Фактический результат:** ответа нет в течение 15 секунд (ReadTimeout). Остальные запросы отвечали за 90–200 мс.

**Ожидаемый результат:** быстрый ответ 400 с описанием ошибки.

## BUG-6. Ошибка пароля возвращается как «invalid JSON body»

- **Серьёзность:** Minor
- **Связанных тестов нет** (тесты допускают любой 4xx)

**Шаги воспроизведения**

1. `POST /api/1/register` с телом `{"username": "<уникальный>", "password": ""}`.
2. `POST /api/1/autorize` с существующим username и паролем `nope` (валидный JSON).

**Фактический результат:** оба запроса — 400 `{"error": "invalid JSON body"}`, хотя JSON корректен. При этом неизвестный пользователь даёт 401 `invalid username or password`.

**Ожидаемый результат:** сообщение, соответствующее причине (пароль пустой или слишком короткий; неверные данные при авторизации — 401). Если у пароля есть ограничение длины, оно должно быть описано.

## BUG-7. При неверном типе `price` перепутаны поля `message` и `status`

- **Серьёзность:** Minor

**Шаги воспроизведения**

1. `POST /api/1/item` с `"price": "100"` (или `99.99`).

**Фактический результат:** 400 `{"result": {"message": "", "messages": {}}, "status": "не передано тело объявления"}`: текст ошибки лежит в `status`, `message` пуст, текст не отражает причину (неверный тип цены).

**Ожидаемый результат:** в других ошибках `status` содержит код (`"400"`), а текст лежит в `result.message`; сообщение должно называть поле `price`.

## BUG-8. `DELETE` несуществующего объявления: код 404, но в теле `status: "500"`

- **Серьёзность:** Minor

**Шаги воспроизведения**

1. Создать и удалить объявление, затем повторить `DELETE /api/2/item/{id}`.

**Фактический результат:** HTTP 404, тело `{"result": {"message": "", "messages": null}, "status": "500"}`: код в теле противоречит HTTP-коду, текст пуст.

**Ожидаемый результат:** согласованный код в теле (`"404"`) и осмысленное сообщение, как у `GET` (`item <id> not found`).

## BUG-9. Нулевые значения отклоняются как «поле обязательно»

- **Серьёзность:** Minor (требует уточнения требований)
- **Связанный тест:** `tests/test_statistics.py::test_statistics_zero` (TC-STAT-03, динамический xfail)

**Шаги воспроизведения**

1. `POST /api/1/item` с `"price": 0`.

**Фактический результат:** 400 `поле price обязательно`, хотя поле передано. Вероятно, ноль воспринимается как «не передано». Для нулевой статистики (`likes: 0`) подтвердите ручной проверкой.

**Ожидаемый результат:** либо принять 0 как допустимое значение, либо вернуть сообщение «цена должна быть больше 0». Для счётчиков (лайки, просмотры) ноль — естественное значение у нового объявления.

## Наблюдения (не дефекты)

- Стенд общий и периодически «зависает» на минуту-две: таймаут получали разные запросы, в том числе короткие (диагностика `scripts/diag_hang.py`, `docs/diag_hang_report.md`). Зависание не привязано к входным данным, поэтому дефектом сервиса не оформлено; тесты защищены от него (stand-guard в `conftest.py`).
- Невалидный длинный id: `GET /api/1/statistic/<300 символов>` отвечает 400, а `GET /api/2/statistic/<300 символов>` — 404.
- Формат ошибок различается между ручками: `{"error": "..."}` (401, регистрация) и `{"result": {...}, "status": "..."}` (остальные).
- `createdAt` содержит часовой пояс дважды: `2026-10-15 21:44:57.381678 +0300 +0300`.
- Чтение объявления и статистики возвращает список из одного элемента, а не объект; в объявлении поле называется `sellerId`, а при создании — `sellerID`.
- Любой авторизованный пользователь может читать чужие объявления (`GET /api/1/item/{id}` → 200). Для публичных объявлений это нормально.
