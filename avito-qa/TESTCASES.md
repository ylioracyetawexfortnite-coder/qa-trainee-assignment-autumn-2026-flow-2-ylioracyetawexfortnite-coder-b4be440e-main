# Тест-кейсы

Сервис: микросервис пользователей, объявлений и статистики (`https://qa-internship.avito.com`).
Каждый кейс реализован автотестом; ID кейса вынесен в название теста (`@allure.title`) и виден в отчёте.
Параметризованные кейсы дают несколько запусков (всего ~226 проверок на 77 кейсов).

## Применённые техники тест-дизайна

| Техника | Где применена |
|---|---|
| Эквивалентные классы | валидные и невалидные типы полей (`name`, `price`, `sellerID`, `statistics`), форматы id |
| Граничные значения | длины `username`/`password`/`name` (1, 255, 256, 1000, 10000), `price` (-1, 0, 1, 2³¹-1, 2³¹, 2⁶³-1, 2⁶³), статистика (0, -1, 2³¹-1) |
| Таблица решений | доступ к защищённым ручкам: нет токена / битый токен / чужой токен / чужой sellerID |
| Переходы состояний | жизненный цикл объявления: создано → прочитано → удалено → повторное удаление / чтение |
| Предугадывание ошибок | инъекции (SQL, XSS), подмена `X-UserId`, старая версия DELETE, несуществующая версия API |
| Попарное / комбинаторное | поле × неверный тип, ручка × способ нарушения авторизации |
| Нефункциональные | время ответа, формат `Content-Type`, параллельное создание, утечки внутренних деталей в ошибках |

## Как читать ожидаемые результаты

В задании не описаны коды ошибок и правила валидации, поэтому кейсы делятся на три вида:

- **Строгие**: поведение однозначно следует из условия (нет токена → 401, нет объявления → 404, чужой sellerID запрещён). Тест падает при любом отклонении.
- **«Отклонить»**: заведомо некорректные данные (пустое имя, отрицательная цена, неверный тип). Ожидаем любой код 4xx и **не** 5xx.
- **«Принять или отклонить»**: спорные границы (цена 0, имя 256 символов и т. п.). Допустимы и 2xx, и 4xx, но не 5xx. Если значение принято, оно должно сохраниться без искажений.

Идентификатор продавца может приходить как `sellerID` или `sellerId`, ответ чтения — как объект или список из одного объекта. Тесты это учитывают.

Общие предусловия для всех кейсов, кроме отдельно оговорённых: стенд доступен; пользователь создаётся динамически (регистрация + авторизация) с уникальным логином; созданные объявления удаляются после теста.

## 1. Регистрация и авторизация (`tests/test_auth.py`)

| ID | Кейс | Шаги | Ожидаемый результат |
|---|---|---|---|
| TC-AUTH-01 | Успешная регистрация | `POST /api/1/register` с уникальными username и password | 201; в теле `id` (целое > 0) и `username` равный отправленному; пароль не возвращается |
| TC-AUTH-02 | Уникальность id | Зарегистрировать двух пользователей | `id` различаются |
| TC-AUTH-03 | Дубликат username | Зарегистрировать пользователя, повторить регистрацию с тем же username и другим паролем | 4xx; исходный пользователь авторизуется со старым паролем |
| TC-AUTH-04 | Некорректное тело регистрации | Отправить: `{}`; без username; без password; пустые username/password; `null`; числа и массив вместо строк | 4xx, не 5xx |
| TC-AUTH-05 | Битый JSON | Отправить `{not json`, пустое тело, `[]`, `null` с `Content-Type: application/json` | 4xx |

| TC-AUTH-15 | Повторные логины | Авторизоваться дважды, использовать оба токена | Оба токена работают |
| TC-AUTH-16 | Публичные ручки | Регистрация и авторизация без заголовка Authorization | 201 и 200 |
| TC-AUTH-17 | Неподдерживаемые методы | GET/PUT/DELETE на `/register` и `/autorize` | 4xx |

## Кейсы, которые падают из-за дефектов сервиса (xfail)

Прогон на стенде 2026-10-15 (см. [docs/probe_report.md](docs/probe_report.md)) показал расхождения с ожиданиями.
Эти тесты помечены `xfail`, причина указана в [BUGS.md](BUGS.md). `strict=True` означает, что после
исправления дефекта тест сообщит о неожиданном прохождении.

| Кейс | Дефект | Режим |
|---|---|---|
| TC-SEC-09 удаление чужого объявления | BUG-1 | strict |
| TC-STAT-06 статистика после удаления (v1, v2) | BUG-2 | strict |
| TC-ITEM-08 отрицательная цена | BUG-3 | `-1` strict, остальные нет |
| TC-ITEM-11 отрицательная статистика | BUG-4 | `likes` strict, остальные нет |
| TC-AUTH-04 `{}` при регистрации | BUG-5 | нестрогий (дефект требует перепроверки) |
| TC-STAT-03 нулевая статистика | BUG-9 | динамический xfail, если нули отклоняются |

## Ограничения

- API не содержит ручки удаления пользователей, поэтому созданные тестовые пользователи остаются на стенде. Это компенсируется уникальными логинами (`qa_<uuid>`).
- Правила валидации в задании не описаны, поэтому спорные границы проверяются в режиме «принять или отклонить». После первого прогона на реальном стенде строгость можно повысить (см. README, раздел «Что делать с упавшими тестами»).
