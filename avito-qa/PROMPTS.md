# Использование ИИ

Я использовал ИИ-ассистента (Claude) как инструмент: для разбора задания, проектирования тест-кейсов,
написания кода тестов, локального мока и документации. Решения о том, что считать дефектом, а что нет,
принимал я по результатам запусков на стенде. Секреты (токены, пароли) в промпты не передавались.

## Как строилась работа

| 1. Анализ | Передал текст задания и Postman-коллекцию, попросил разобрать ручки и зоны риска | Выбрал стек (pytest, requests, Allure) и структуру репозитория |
| 2. Сборка | Попросил собрать проект и подробную инструкцию запуска | Развернул окружение, запустил тесты |
| 3. Разведка стенда | Передал `probe_report.md` с ответами сервиса | Подгонял ожидания тестов под фактическое поведение API, оформил дефекты в `BUGS.md`, пометил тесты `xfail` |
| 4. Нестабильность | Передал выводы прогонов с таймаутами | Запустил диагностику `scripts/diag_hang.py` на стенде, получил данные |
| 5. Итоговая проверка | Передал результаты диагностики | Проверил гипотезу «длинный id вешает сервис»: не подтвердилась, зависания плавающие и не зависят от входных данных. Новый дефект не заводил |

## Что дало использование ИИ

- Быстрый старт: структура проекта и базовый набор из 226 проверок за один заход.
- Локальный мок сервиса, на котором можно проверять сам проект без нагрузки на общий стенд.
- Защита тестов от зависаний общего стенда (ожидание восстановления, повторные попытки), проверенная на моке с имитацией зависаний.

## Как я проверял результат

- Каждое допущение ИИ о поведении API сверялось с ответами стенда; при расхождении исправлялись тесты.
- Гипотезы ИИ о причинах падений проверялись отдельной диагностикой, а не принимались на веру.
- Итоговый прогон на стенде: 214 passed, 11 xfailed, 1 xpassed.
- Дефекты в `BUGS.md` описаны по фактическим ответам стенда.
