# API-тесты микросервиса пользователей, объявлений и статистики

Автотесты на Python (pytest + requests) для `https://qa-internship.avito.com`.
Тест-кейсы описаны в [TESTCASES.md](TESTCASES.md), найденные дефекты — в [BUGS.md](BUGS.md),
использованные промпты ИИ — в [PROMPTS.md](PROMPTS.md).

## Что внутри

```
├── src/                 клиент API, генераторы данных, JSON-схемы, настройки
├── tests/               тесты (conftest.py — фикстуры и cleanup)
├── tools/mock_server.py локальный мок сервиса для офлайн-проверки самого проекта
├── scripts/probe.py     разведка реального стенда: коды и тела ответов в probe_report.md
├── scripts/diag_hang.py диагностика зависаний: какие запросы вешают стенд и как долго он «отходит»
├── docs/                пример Allure-отчёта (docs/allure-report-example.html)
├── pyproject.toml       настройки pytest, ruff, black
└── .env.example         шаблон настроек окружения
```

Принципы: все данные создаются динамически (уникальные логины и названия; один общий пользователь на прогон, отдельные пользователи там, где нужен пустой список), тесты не зависят от порядка
запуска, а созданные объявления удаляет в teardown. Bearer-токен берётся через `/api/1/autorize`.

## Требования

- Python 3.10 или новее (`python --version`)
- Доступ в интернет к `https://qa-internship.avito.com`
- Для Allure-отчёта: Allure CLI (по желанию, см. ниже)

## Установка

```bash
# 1. Перейдите в папку проекта
cd avito-qa

# 2. Создайте и активируйте виртуальное окружение
python -m venv .venv
source .venv/bin/activate          # macOS / Linux
.venv\Scripts\activate             # Windows (cmd или PowerShell)

# 3. Установите зависимости
pip install -r requirements.txt

# 4. (по желанию) создайте файл настроек
cp .env.example .env               # Windows: copy .env.example .env
```

Настройки (переменные окружения или `.env`):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `BASE_URL` | `https://qa-internship.avito.com` | адрес сервиса |
| `REQUEST_TIMEOUT` | `15` | таймаут запроса, с |
| `REGISTER_ATTEMPTS` | `3` | сколько раз фикстура пробует создать пользователя при таймаутах стенда |
| `MAX_RESPONSE_TIME` | `3` | порог времени ответа в нефункциональных тестах, с |
| `STAND_RECOVERY_WAIT` | `240` | сколько секунд ждать оживления стенда после таймаута, прежде чем остановить прогон |

## Запуск тестов

```bash
pytest                      # все тесты
pytest -m smoke             # только основные позитивные сценарии
pytest -m "negative or boundary"
pytest -m security          # авторизация, доступ, подмена пользователя
pytest -m e2e               # сквозной сценарий
pytest tests/test_auth.py   # один файл
pytest -k test_statistics         # по части имени теста
pytest -n 4                 # параллельно (нужно: pip install pytest-xdist)
```

Маркеры: `smoke`, `negative`, `boundary`, `security`, `nonfunctional`, `e2e`.

## Allure-отчёт

Результаты каждого прогона пишутся в `allure-results/` (в них есть шаги, запросы и ответы; токены и пароли
маскируются). Чтобы получить HTML-отчёт, нужен Allure CLI:

```bash
npm install -g allure-commandline            # нужны Node.js и Java 8+
# или: brew install allure  /  scoop install allure

allure serve allure-results                  # открыть отчёт в браузере
allure generate allure-results -o allure-report --clean --single-file   # сохранить файл
```

Пример готового отчёта лежит в `docs/allure-report-example.html`
(открывается двойным кликом). **Он собран на локальном моке с поведением реального стенда (`MOCK_BUGS=real`), а не на самом стенде**;
перед сдачей замените его своим отчётом, сформированным после прогона на стенде.

## Линтер и форматтер

Используются `ruff` (линтер) и `black` (форматтер), правила — в `pyproject.toml` (длина строки 100).

```bash
ruff check .          # проверка
ruff check --fix .    # проверка с автоисправлением
black .               # форматирование
black --check .       # только проверить, ничего не менять
```

## Проверка проекта без реального стенда

Запустите мок, написанный по описанию из задания, и направьте на него тесты:

```bash
# терминал 1
python tools/mock_server.py --port 8080
# терминал 2
BASE_URL=http://127.0.0.1:8080 pytest          # Windows PowerShell: $env:BASE_URL="http://127.0.0.1:8080"; pytest
```

Все тесты на моке проходят. Чтобы убедиться, что тесты ловят дефекты, запустите мок с «багами»:
`MOCK_BUGS=spoof,noauth_delete,double_delete_ok,neg_price python tools/mock_server.py`.

## Разведка реального стенда

```bash
python scripts/probe.py
```

Скрипт выполнит около 50 запросов и сохранит коды и тела ответов в `probe_report.md`. По нему
видно, как стенд ведёт себя на самом деле (формат ошибок, коды, формат ответа чтения/статистики).

## Что делать с упавшими тестами

Задание допускает падающие тесты, если у них есть понятное обоснование и баг-репорт. Порядок:

1. Запустите `pytest` на реальном стенде и посмотрите на упавшие тесты в отчёте.
2. Для каждого падения решите, дефект это или неверное допущение теста (в TESTCASES.md описано, какие кейсы строгие, а какие допускают разные коды).
3. Если это дефект сервиса — опишите его в `BUGS.md` (шаблон там же) и пометьте тест, чтобы он падал «по-честному»:

   ```python
   @pytest.mark.xfail(reason="BUG-1: см. BUGS.md", strict=True)
   def test_...():
   ```

   `strict=True` означает, что при исправлении дефекта тест сам сообщит о неожиданном прохождении.
4. Если это неверное допущение теста — поправьте ожидание в тесте и в `TESTCASES.md`.

## Результаты прогона на стенде

По разведке стенда (`docs/probe_report.md`) найдено 9 дефектов, описанных в `BUGS.md`. Тесты на пять
из них помечены `xfail`, поэтому на стенде ожидаемый итог — тесты проходят, а известные дефекты
показаны как `xfailed` (если какого-то дефекта не окажется, будет `xpassed`; для `strict`-тестов это ошибка).
Зависание запроса ловится как таймаут (`REQUEST_TIMEOUT`) и превращается в понятную ошибку теста.
Стенд общий и иногда тормозит, поэтому фикстуры используют одного пользователя на весь прогон
(`shared_user`), а `fresh_user` создаётся только там, где нужен пустой список объявлений; при
таймауте регистрация повторяется. Если ошибки подготовки всё равно появляются — запустите `pytest`
позже или увеличьте `REQUEST_TIMEOUT`.

**Защита от каскада таймаутов (stand-guard).** Если какой-то запрос завис, следующий тест не стартует,
пока стенд не начнёт снова создавать объявления (проверка раз в 5 с, не дольше `STAND_RECOVERY_WAIT`).
Поэтому одно зависание даёт одно падение у теста, который его вызвал, а не серию ложных ошибок
у соседей. Если стенд не ожил за `STAND_RECOVERY_WAIT`, прогон останавливается с кодом 2.
Тест с пометкой `xfail`, который упал по таймауту, показывается как обычное падение, а не как
«ожидаемый дефект» (исключение: BUG-5, где зависание и есть дефект).

`python scripts/diag_hang.py` отдельно проверяет подозреваемые запросы (длинные id, большие числа)
и пишет отчёт в `docs/diag_hang_report.md`.

Мок с поведением реального стенда: `MOCK_BUGS=real python tools/mock_server.py`.

## Известные ограничения

- В API нет ручки удаления пользователей, поэтому тестовые пользователи (`qa_<uuid>`) остаются на стенде.
- Стенд общий: тесты используют только собственные данные и не полагаются на чужое состояние.
